|---|---|

## Key design decisions

- **Reference.** Generated by the handler in `preSave()` and kept in memory
  for the request, keyed by the submission UUID. With results disabled the
  submission has no ID, so the reference depends neither on the submission
  ID nor on the serial number. It is exposed as a token, available in the
  emails and in the confirmation.
- **Real email result.** Webform does not report whether an email was
  actually sent. The module decorates the core `plugin.manager.mail` service
  and records the result of the Webform messages that `hook_mail_alter()`
  marked for a tracked submission. It never records addresses.
- **End of processing.** File deletion, the delivery record and the alert
  run in `hook_webform_submission_insert()`, which Webform invokes after all
  handlers, even when results are disabled. The outcome therefore does not
  depend on handler weights.
- **Acknowledgement replaced on failure.** The handler settings name the
  email handler that sends to the recipient and the one that sends the
  acknowledgement. When the recipient email fails, the acknowledgement is
  cancelled and the visitor receives a failure email instead. The address is
  kept in memory only, for the duration of the request.
- **No public page.** The failure screen is rendered in the inline
  confirmation, so the module requires inline confirmations. A dedicated
  failure page may be added later as an option.
- **Uploaded files.** Deleted with the core File API as soon as the emails
  have been sent, whatever their result.

## Settings

| Setting | Storage | Reason |
|---|---|---|
| Reference prefix, retention period, default texts | Configuration `webform_handoff.settings` | Deployed with the site configuration |
| Recipient and acknowledgement handlers, failure display | Handler configuration, in the webform | Per form |
| Contact details shown on failure, alert recipients | State | Site-specific, not overwritten by deployments |

## Known limitation

When an email cannot be sent, Drupal core (channel `mail`) and some mail
backends (for example Symfony Mailer Lite) write the addresses, and possibly
the subject, to the site log. This happens outside the module. Sites should
limit the log retention or send logs to a protected destination.
